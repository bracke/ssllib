IMPLEMENTATION PROMPT: ssllib — PURE ADA TLS 1.2 AND TLS 1.3 LIBRARY

Implement a complete, production-oriented Ada 2022 TLS library named `ssllib`.

This is not a prototype, wrapper, partial codec, proof of concept, or minimal release. Implement the complete V1 specified below. Do not silently narrow scope, leave security-critical functionality as TODOs, or substitute insecure temporary behavior.

======================================================================
1. PROJECT IDENTITY
======================================================================

Project name and Alire crate:
    ssllib

Root Ada package:
    SSL

Child test and tooling crate:
    ssllib_tests

Language:
    Ada 2022

License:
    MIT for project-owned runtime code, tests, Ada tooling, examples,
    generated project-owned code, and documentation. Preserve licenses and
    attribution for imported vectors, fixtures, and reference material.

Purpose:
    Provide TLS 1.3 and a deliberately restricted modern TLS 1.2
    implementation for authenticated, confidential, integrity-protected
    bidirectional byte streams over caller-supplied transports.

The name `ssllib` does not imply support for obsolete SSL protocols. Do not
implement SSL 2.0 or SSL 3.0.

The project is Ada-only. Do not provide a C ABI, C bindings, exported C
symbols, OpenSSL compatibility API, foreign-language binding foundations, or
architecture organized around future C compatibility.

======================================================================

Use `cryptolib`:
    https://github.com/bracke/cryptolib

`cryptolib` is the sole provider of:
    - hashes and HMAC;
    - HKDF and reusable TLS 1.3 KDF primitives;
    - AES-GCM and ChaCha20-Poly1305;
    - secure randomness;
    - constant-time comparison;
    - secure wiping;
    - X25519, NIST ECDH, and enabled finite-field DH;
    - EdDSA, ECDSA, RSA signing and verification;
    - PEM, DER, ASN.1, PKCS#8, encrypted PKCS#8, and PKCS#12;
    - local identity/private-key ownership;
    - X.509 parsing and signature verification;
    - certificate path building and validation;
    - certificate-purpose checks;
    - DNS and IP service-identity matching;
    - CRL and OCSP processing;
    - certificate and SPKI fingerprints.

Do not duplicate any cryptographic, ASN.1, X.509, PKIX, OCSP, or CRL
implementation in `ssllib`.

Use `truststores`:
    https://github.com/bracke/truststores

`truststores` is the sole provider of:
    - native system trust-anchor discovery and loading;
    - explicitly selected NSS trust sources;
    - explicitly selected Java trust stores;
    - platform trust-source metadata and diagnostics.

Native system trust is the default client trust domain. NSS and Java stores
are opt-in and must not be silently merged into the default trust domain.

Use `hostkit`:
    https://github.com/bracke/hostkit

Use `hostkit` for every remaining host-specific operation required by runtime
or tooling, including monotonic clocks, process execution, temporary
filesystem support, platform-safe path handling, process termination, and
other genuine host differences. Do not create private Linux, Windows, or
macOS implementations inside `ssllib` for functionality belonging in
`hostkit`.

Use AUnit in `ssllib_tests`.

Use `project_tools` in `ssllib_tests` for all build, test, proof,
documentation, verification, packaging, release, and repository automation.

The runtime crate must not depend on AUnit or `project_tools`.

6. CORE ARCHITECTURE
======================================================================

Implement one deterministic, transport-independent protocol engine.

The engine:
    - never opens sockets;
    - never blocks or sleeps;
    - never reads global clocks;
    - never performs hidden environment lookup;
    - never launches background tasks;
    - consumes caller-supplied encrypted bytes;
    - produces caller-drained encrypted bytes;
    - accepts bounded application plaintext;
    - exposes authenticated application plaintext;
    - returns explicit semantic events;
    - reports exactly why progress is blocked.

Build the blocking API, stream API, synchronized wrapper, and event-loop
integration on this same engine. Do not create separate blocking and
nonblocking protocol stacks.

Connections are limited, single-use objects. They cannot be reset or reused
after close or failure.

Lifecycle:
    - Uninitialized
    - Ready
    - Handshaking
    - Established
    - Closing
    - Closed
    - Failed

TLS 1.2 and TLS 1.3 must have separate explicit state machines. Do not encode
protocol state as scattered Boolean fields.

======================================================================
11. RECORD LAYER
======================================================================

Implement explicit codecs for the five-byte TLS record header. Never use
unchecked wire-to-record conversion.

Support incremental parsing at every byte boundary, multiple records per
input buffer, and trailing partial records.

Maintain separate read and write traffic states:
    - epoch;
    - traffic secret;
    - AEAD context;
    - IV;
    - sequence number;
    - generation;
    - record and byte counters;
    - usage limits;
    - closed state.

TLS 1.3 protected records:
    - outer type application_data;
    - legacy version 0x0303;
    - five-byte header as AEAD associated data;
    - inner plaintext is content, inner type, zero padding;
    - remove padding only after successful authentication.

Nonce:
    - encode 64-bit sequence big-endian;
    - left-pad to IV size;
    - XOR static IV.

Never wrap a sequence number or reuse a nonce/key pair.
Increment only after successful protection/authentication.

On AEAD failure:
    - expose no plaintext;
    - do not try alternate keys or sequence values;
    - map to bad_record_mac;
    - terminate.

Support record_size_limit, bounded padding, fragmented handshake streams,
multiple messages in one record, application reads across record boundaries,
bounded empty records, and narrowly permitted TLS 1.3 compatibility CCS.

Outbound priority:
    fatal alert, close_notify, handshake/control, KeyUpdate, application data.

======================================================================
12. TLS 1.3
======================================================================

ClientHello:
    - legacy_version 0x0303;
    - fresh 32-byte random from cryptolib;
    - non-empty 32-byte legacy session ID by default;
    - configured suites;
    - null compression only;
    - deterministic extension order;
    - pre_shared_key last.

Implement and validate:
    server_name, status_request, supported_groups, signature_algorithms,
    signature_algorithms_cert, ALPN, record_size_limit, supported_versions,
    psk_key_exchange_modes, key_share, pre_shared_key, cookie, and
    certificate_authorities where useful.

Reject duplicate extensions. Enforce exact contexts and unsolicited-response
rules. Keep unknown numeric IDs for diagnostics and ignore them only when the
protocol permits.

HelloRetryRequest:
    - exact special random;
    - at most once;
    - validate version and requested group;
    - reject request for a group already supplied with a valid share;
    - use synthetic message_hash transcript transformation;
    - preserve random, legacy session ID, SNI, ALPN, suites, and versions;
    - echo cookie exactly;
    - recalculate binders.

Transcript:
    - exact handshake type, three-byte length, and body;
    - no record header;
    - exact received bytes, not a canonical re-encoding;
    - exact locally queued bytes;
    - snapshot before CertificateVerify and Finished;
    - SHA-256/SHA-384;
    - nonfinalizing snapshot;
    - HRR support.

Key schedule:
    Use cryptolib primitives but own all TLS orchestration:
        early secret, binder key, binder Finished key, handshake secret,
        client/server handshake traffic secrets, Finished keys, master
        secret, application traffic secrets, exporter master secret,
        resumption master secret, and traffic update secrets.

Tie derivation operations to named transcript milestones. Do not expose raw
secret getters.

Implement exact directional key-installation timing.

Authentication:
    - parse bounded Certificate;
    - use cryptolib for X.509;
    - use truststores-derived anchors;
    - build/validate path;
    - validate purpose and key usage;
    - verify expected DNS/IP identity;
    - evaluate revocation and pinning;
    - verify CertificateVerify separately;
    - verify Finished separately.

CertificateVerify input:
    64 ASCII spaces, exact TLS 1.3 context string, zero separator, transcript
    hash.

Finished:
    derive Finished key, HMAC transcript hash, constant-time compare, append
    message only after successful verification.

Support optional and required client authentication. Empty client
Certificate is allowed only when policy permits and is never followed by
CertificateVerify.

======================================================================
13. RESTRICTED TLS 1.2
======================================================================

Use a separate state machine.

Require ECDHE, AEAD, SHA-256/384 PRF, EMS, and null compression.

Implement:
    ClientHello, ServerHello, Certificate, ServerKeyExchange,
    optional CertificateRequest, ServerHelloDone, optional client Certificate,
    ClientKeyExchange, optional CertificateVerify, ChangeCipherSpec, Finished.

ServerKeyExchange verification covers:
    client_random || server_random || exact encoded ECDHE parameters.

Implement TLS 1.2 PRF/P_hash with SHA-256 and SHA-384.

EMS:
    master_secret = PRF(premaster, "extended master secret", session_hash)

Reject peers not negotiating EMS. Never store or resume a non-EMS session.

Derive the AEAD key block in the protocol-defined order.

ChangeCipherSpec is the real TLS 1.2 epoch switch. CCS itself is plaintext and
the following record uses the new keys. Reject malformed, early, repeated, or
unexpected CCS.

Finished:
    PRF(master_secret, "client finished"/"server finished",
        transcript_hash), 12 bytes, constant-time comparison.

Implement the distinct TLS 1.2 AES-GCM and ChaCha20-Poly1305 record formats
and associated data.

No renegotiation and no TLS 1.2 key update. Close and reconnect before key-use
or sequence limits.

Implement downgrade markers and reject legacy downgrade.

======================================================================
14. ALPN, SNI, AND EXTENSIONS
======================================================================

Use a closed internal extension registry with explicit wire IDs and context
rules. No plugin architecture.

ALPN names are opaque non-empty byte strings, length 1..255, with no UTF-8
assumption. Reject duplicates. Preserve order.

Support:
    - server-order selection;
    - client-order selection;
    - application selector;
    - optional or required ALPN.

If required and no overlap, fail with no_application_protocol.

Bind selected ALPN into resumption. Never resume under a different ALPN.

SNI uses a validated DNS-name type:
    - defined UTF-8/IDNA conversion;
    - normalized ASCII A-label;
    - no IP literals;
    - no locale-sensitive case handling.

Keep transport destination, SNI routing name, and expected authenticated
identity separate.

Support exact names, valid single-label leftmost wildcards, a single explicit
default identity, and reject-unrecognized policy.

Credential selection must deterministically combine SNI, wildcard
specificity, default policy, protocol, peer signature schemes, private signing
capability, certificate key type, ALPN restrictions, configured priority, and
stable insertion order.

======================================================================
15. CREDENTIALS, TRUST, REVOCATION, AND PINNING
======================================================================

Local credentials are controlled wrappers around cryptolib identity/signer
objects. Never expose private key bytes or parameters.

Support PEM, DER+PKCS#8, encrypted PKCS#8, PKCS#12, loaded cryptolib
identities, and external signers.

No filesystem reads or password prompts during handshake.

Passwords and decrypted key material use secret-controlled buffers and are
wiped after use.

Validate identity structure, key/certificate match, key type, usable signing
schemes, key usage, and bounds at load time.

External signers report capabilities and sign exact message/digest inputs.
They may require serialized access. Catch provider exceptions.

Trust:
    - native system trust is the default;
    - NSS and Java require explicit selection;
    - explicit PEM/parsed anchors supported;
    - trust snapshots immutable;
    - refresh creates new configuration;
    - required unavailable or empty sources fail closed;
    - peer self-signed certificates are never implicit anchors.

Validation pipeline:
    decode, parse, bounded path build, path validation, purpose, key usage,
    DNS/IP identity, revocation, pinning, CertificateVerify, Finished.

Use SAN only. No Common Name fallback.

Revocation:
    - Disabled
    - Check_When_Available
    - Require_Valid_Status
    - Require_Stapled_OCSP

No hidden network fetching. Use stapled or caller/provider-supplied OCSP/CRLs.
Explicit revoked status always fails.

Pin types:
    - certificate SHA-256
    - SPKI SHA-256

Pinning:
    - No_Pinning
    - Require_Valid_Path_And_Pin
    - Pin_Only

Pin scopes include identity, optional endpoint/ALPN, and activation periods.
Pinning must not silently disable identity matching.

======================================================================
16. SESSIONS AND TICKETS
======================================================================

TLS 1.3 supports server-issued NewSessionTicket, PSK derivation from the
resumption master secret and ticket nonce, psk_dhe_ke, and full-handshake
fallback. No external PSKs and no 0-RTT.

TLS 1.2 supports stateless tickets only and requires EMS.

Bind sessions to:
    expected identity, endpoint label, SNI, ALPN, protocol, compatible
    cipher/hash, trust fingerprint, configuration fingerprint, client
    credential/authentication state, application Security_Context_ID,
    authentication reference, and lifetime metadata.

Expose fresh certificate authentication and PSK-resumed authentication as
different metadata.

Provide client cache interface and bounded task-safe memory implementation.
Use deterministic expiration and LRU-style eviction. Cache failure normally
falls back to full handshake.

Implement exact TLS 1.3 binder construction and verification with
constant-time comparison and wiped intermediates.

Use versioned authenticated-encrypted ticket formats. Authenticate before
parsing. Include explicit protocol family, purpose, key ID, issue/expiry,
security bindings, and session state. Never use raw Ada record persistence.

Invalid, unknown, expired, corrupt, or mismatched tickets normally become
unusable candidates and trigger a full handshake without a useful oracle.

Ticket key states:
    Pending, Active, Decrypt_Only, Expired.

Normally exactly one active encryption key. Retain bounded decrypt-only keys.
Support explicit application-managed keys and in-memory library rotation.
Never persist or distribute keys implicitly.

Persisted client sessions must be protected using an explicit application or
library persistence key. No unencrypted normal mode and no hidden file I/O.

======================================================================
17. KEYUPDATE, EXPORTERS, AND CHANNEL BINDING
======================================================================

Track per-direction/per-generation record and byte usage.

Schedule TLS 1.3 KeyUpdate before safe limits. At hard limits, prohibit another
record and fail closed if update cannot complete.

KeyUpdate message is encrypted under the old key. Install the new key only
after queueing/sending that message. Reset sequence to zero. Protect against
update floods.

Exporters:
    - available only after successful handshake;
    - TLS 1.3 uses exporter master secret;
    - TLS 1.2 uses EMS-authenticated master secret and PRF;
    - explicit label and context-presence flag;
    - bounded secret output;
    - no exporter-secret getter.

Channel binding:
    - tls-exporter;
    - tls-server-end-point;
    - tls-unique only for qualifying TLS 1.2;
    - never tls-unique for TLS 1.3.

Treat channel-binding values as sensitive controlled data.

======================================================================
18. SHUTDOWN AND FAILURE
======================================================================

Support send-only and bidirectional close_notify plus abortive close.

After sending close_notify, reject application writes but permit policy-
appropriate reads. After receiving close_notify, reject later peer application
data and expose clean EOF.

Transport EOF without authenticated close_notify is truncation, never clean
closure.

Fatal failure:
    preserve primary error, map centralized alert, queue alert if safe, reject
    application I/O, allow alert ciphertext drain, wipe secrets when no longer
    needed, and retain immutable failure information.

Do not expose buffered application plaintext after fatal failure detection.

Finalization never performs I/O or blocking work. It wipes secrets and releases
storage. Graceful close is explicit.

======================================================================
19. ERRORS, ALERTS, DIAGNOSTICS, AND KEY LOGGING
======================================================================

Errors contain stable category, explicit numeric code, origin, fatal flag,
optional alert, protocol/connection/handshake state, provider information,
bounded parameters, retry classification, and disclosure classification.

Do not derive numeric values from enum positions.

Preserve the first terminal semantic failure. Bound secondary failures.

Centralize TLS 1.2/TLS 1.3 alert mapping.

Support all required alert descriptions and preserve unknown peer alert
numeric values without inventing semantics.

Diagnostics are structured events with levels:
    Off, Errors_Only, Connection_Summary, Handshake_Summary,
    Detailed_Protocol.

Redaction:
    Strict, Operational, Explicit_Debug.

Never log keys, passwords, secrets, PSKs, binders, ticket plaintext, key-log
material, or application plaintext.

Provide optional metrics/tracing sinks without runtime framework dependency.

Place key logging under SSL.Unsafe.Key_Logging. It is disabled by default,
enabled only explicitly per configuration, uses an application sink, never
opens files, never reads enabling environment variables, supports standard
key-log labels, and wipes temporary formatting buffers.

deletion, length corruption, duplicate/reordered extensions, tag/signature

permanent corpus.

Every hostile input must yield valid behavior, structured rejection, or
bounded need-more-input. Never unhandled ordinary exception, infinite loop,
unbounded allocation, unauthenticated plaintext, or secret leakage.

Test resource limits at limit-1, limit, limit+1, and huge declared length with
no payload. Test CPU work bounds.

Test secret cleanup through test-only wipe observers and scan diagnostics for
recognizable seeded secret patterns.

Test concurrency and callback exceptions/reentrancy.

======================================================================
28. V1 ACCEPTANCE
======================================================================

V1 is complete only when:
    - TLS 1.3 and restricted TLS 1.2 client/server are complete;
    - every required suite, group, and signature family interoperates;
    - server and client certificate authentication work;
    - cryptolib is the only cryptographic/PKI implementation;
    - truststores is the only native trust integration;
    - hostkit owns remaining host differences;
    - blocking and nonblocking APIs share one engine;
    - partial I/O and bounded backpressure are correct;
    - close_notify and truncation are distinct;
    - session resumption works without 0-RTT;
    - SNI, ALPN, OCSP, pinning, KeyUpdate, exporters, and channel binding work;
    - hostile inputs remain bounded;
    - no unauthenticated plaintext is exposed;
    - nonce reuse is structurally impossible;
    - ordinary protocol errors never escape as unhandled exceptions;
    - stable errors/alerts and secret-safe diagnostics are complete;
    - key logging is explicitly unsafe and off by default;
    - all tooling is Ada through project_tools;
    - release proof, interop, platform, docs, and reproducibility gates pass;
    - every invariant has verification coverage.

Do not declare V1 complete because the project compiles, one handshake works,
ssllib interoperates only with itself, TLS 1.2 is unfinished, authentication
is stubbed, resumption is absent, platform trust is mocked, or release gates
are missing.
